# freeAgent 现状评估与完善方案

> 评估时间：2026-11-10
> 评估对象：`F:\agentBuild\freeAgent`（Python 3.11，纯标准库 + requests/playwright）
> 评估方式：通读 12 个核心模块（agent / engine / gateway / runner / autonomous / planner / sandbox / trust / confirm_gate / task_memory / skills / scheduler），统计 `.agent/traces` 40 条真实轨迹（319 个事件、47 次工具调用）

---

## 0. 结论先行

**这套东西的骨架是对的，问题不在"功能少"，而在"它会把自己没干成的事报成成功"。**

三条最关键的发现：

1. **53% 的"成功"是假的。** 36 个完整任务里 19 个 `ok=true` 且**一次工具都没调用**；其中 5 个的"最终答案"是网页模型的限流错误页原文（`ChatGLM 请求过于频繁，请稍后再试`），却被记成 `stop_reason=finished, ok=true`。
2. **网页通道没有任何错误页识别。** 限流、登录失效、验证码都会被当成正常回答写进 trace 和长期记忆，等于把污染数据喂给下一次任务。
3. **工程地基缺失。** 没有 git、没有 pytest、没有 CI；89 处 `except Exception` 吞异常；`server.py` 单文件 1110 行。改起来没有安全网。

所以方案顺序是：**先补"证据链"（判成功的依据）→ 再补"能力"（工具/模型/记忆）→ 最后补"规模"（并发/评测/安全纵深）**。反过来做，功能越多，假成功越多。

### 2.3 两个典型的"假成功"现场

```
# 20261109-172034-3d26
goal: 帮我统计一下我的f盘有多少个文件夹
thinking(turn=1) → 0 次工具调用
task_end: {"ok": true, "stop_reason": "finished",
           "answer": "ChatGLM\n请求过于频繁，请稍后再试\n本次回答已被终止\n重新回答"}
```

```
# 20261110-120548-2078
goal: 打开我的电脑进入f盘统计文件数量
task_end: {"ok": true, "stop_reason": "finished",
           "answer": "我先确认一下 F 盘是否存在，再帮你打开并统计。"}
```

第二条尤其危险：它说的是"我准备去做"，系统却判定"已经做完"。

### 2.4 失败重试没有被循环检测拦住

```
# 20261110-114845-cb0f
turn 1: run_shell("echo $(echo '56+24' | bc)")  → 拒绝：含 '|'
turn 2: run_shell("echo $(echo 56+24 | bc)")     → 拒绝：含 '|'
turn 3: run_shell("echo $(echo 56+24 | bc)")     → 拒绝：含 '|'
task_end: too_many_failures
```

根因在 `agent.py:304`：

```python
if sig == last_sig and last_ok:   # 只有"上次成功"才算重复
```

失败的重复调用永远不计入 `repeats`，所以"同一动作连续失败"这个最该被熔断的模式反而漏掉了。

### 2.5 Playwright 跨线程问题（executor_error 现场）

```
critique(revision=1): 所有网页模型都失败，最后错误:
It looks like you are using Playwright Sync API inside the asyncio loop
```

网页通道用的是同步 Playwright，却被放在 HTTP 服务的多线程 worker 里跑。这一次直接导致 4 步任务跑了 950 秒后失败（`max_seconds=900` 也没有硬截断，只在循环顶部检查）。

## 4. 完善方案

### 总原则

1. **先判"有没有做到"，再判"做得好不好"**。工具级看返回值，步骤级看确定性断言，任务级看证据链；三层都不许模型自证。
2. **失败要分类**。`sandbox_denied / arg_error / not_found / timeout / channel_error / model_format / refusal` 分开，才能自动决定"重试、换路、降级还是问人"。
3. **外部内容是数据，不是指令**。网页/文件/搜索结果统一打 untrusted 标记，高风险动作在"读过外部内容"之后升级确认。
4. **不为框架而框架**。继续零依赖 + 标准库，不引入 LangChain / 向量库 / FastAPI。

### 阶段 0：止血（1~2 天，必须先做）

> 目标：让"成功"这个词重新有意义。改完重放 40 条历史轨迹，假成功率必须从 53% 降到 0。

| 编号 | 改动 | 文件 | 验收 |
| --- | --- | --- | --- |
| 0-1 | `git init` + 基线提交 + `.gitignore`（`.agent/`、`.venv/`、`__pycache__`） | 仓库根 | `git log` 有 1 条基线；`git status` 干净 |
| 0-2 | 新增 `verifier.py`：`classify_answer()` + `judge_task()` | 新建 | 限流文本 → `channel_error`；纯问答"你好" → `ok`；"查 F 盘"0 工具 → `unverified`；有成功工具 → `verified` |
| 0-3 | `run_task` 收尾改为：`finished` 只是"模型说完了"，`ok` 由 `judge_task` 决定，输出 `stop_reason=unverified/channel_error/refused` | `agent.py` | 重放 2.3 两条轨迹，`ok=false` 且原因正确 |
| 0-4 | 网页通道错误页识别：发送前查登录/验证码，回答后查限流关键词 → 抛 `ChannelError`；`web_router` 换下一个通道 | `web_clients.py`、`web_router.py` | 伪造含"请求过于频繁"的页面 → 不产出 ok |
| 0-5 | 循环检测改为"同签名连续失败也算重复"：失败 2 次注入换路提示，3 次终止 | `agent.py` | 重放 `cb0f`，第 2 次就换路或终止 |
| 0-6 | `runner.execute` 非自主分支 try/finally 保证 `task_end`；异常也写 trace | `runner.py` | 人为让 `gateway.chat` 抛异常 → trace 有 `task_end(executor_error)` |
| 0-7 | `_coerce` 把 `None` 当"未提供"（必填才报错），补默认值 | `engine.py` | `list_dir(max_entries=null)` 成功；新增单测 |
| 0-8 | Critic 解析失败改 fail-closed（`ok=False, reason=校验不可用`），并记录 `critique_unavailable` | `planner.py` | 构造解析失败 → 该步不算通过 |
| 0-9 | 新增 `tests/test_p0.py`（pytest，10~12 条），覆盖 0-2~0-8 | 新建 `tests/` | `pytest -q` 全绿 |

**判定状态机（建议直接照这个实现）**

```
模型不再输出 TOOL_CALL
        │
        ├── 答案命中错误页/限流/登录失效 ──────→ stop_reason=channel_error, ok=False（可重试/降级）
        ├── 本任务成功工具调用 = 0 且目标含动作意图 → stop_reason=unverified, ok=False
        ├── 成功工具调用 > 0 但确定性断言不满足 ──→ stop_reason=unverified, ok=False
        ├── 模型明确说明"做不到/需要用户提供X" ───→ ok=True, stop_reason=refused（诚实拒绝可接受）
        └── 其余 ───────────────────────────→ ok=True, stop_reason=finished
```

动作意图识别不用模型：`打开/进入/查/统计/列出/读/写/改/删/运行/执行/搜索/下载/安装/发送/发布` 这类动词 + 目标里出现路径/文件名/URL/软件名 → `requires_action=True`。宁可多判"未验证"，也不能多判"成功"。

### 阶段 1：可靠（1~2 周）

> 目标：让"能做成"的比例真正提高。每个改动都要有可量化验收。

| 编号 | 改动 | 关键设计 | 验收指标 |
| --- | --- | --- | --- |
| 1-1 | **工具调用抽象 + 原生 function calling** | 新增 `toolcall.py`：`ToolCall(kind=native/text, name, args, raw)`；`ModelCapabilities(native_tools: bool)`；API/Ollama 走 `tools` 参数，网页通道保留文本协议；统一进 `Agent` | 同一任务在 API 通道下 JSON 解析失败率 < 1%；token 消耗下降 ≥ 20% |
| 1-2 | **Observation 结构化** | 工具统一返回 `{ok, output, error:{code,message,hint}, artifacts, truncated, full_ref}`；`engine._normalize` 兼容旧返回值 | 错误码覆盖率 100%；"同一错误重复"次数下降 50% |
| 1-3 | **Schema 增强** | 解析 docstring 的 `参数:` 段生成 `description`；支持 `enum`、`minimum/maximum`、`examples`；`to_prompt()` 改为紧凑格式（描述 + 必填 + 类型），全量 schema 只在需要时注入 | 参数错误率下降（当前 44%/60% 的工具失败里，参数类占多数） |
| 1-4 | **Artifact store** | 大输出（>8KB）落 `.agent/artifacts/<task>/<n>.txt`，上下文只放前 N 行 + 路径 + 行数；新增 `read_artifact(ref, offset, limit)` 工具 | 长文件/长命令不再因截断丢信息；上下文峰值 token 下降 |
| 1-5 | **确定性验证器** | 新增 `checks.py`：写文件→存在+大小+可选 diff；`run_shell`→exit code；`search`→结果数+URL；`xhs_*`→页面元素/数量。Critic 只在确定性检查无法判定时才调用 | 自主任务步骤验收不再依赖 LLM 自证；误判率可测 |
| 1-6 | **上下文预算 + 摘要压缩** | 按模型上下文窗口算预算；超限时生成结构化摘要（`已确认事实 / 未决问题 / 关键工具结果引用`），而不是删消息 | 30 步任务不丢前 10 步的关键结论；有单测 |
| 1-7 | **三层记忆** | `episodes`（现有任务卡，加成功/失败权重与时效衰减）+ `facts`（项目事实/环境事实，可手编）+ `prefs`（用户偏好）；T1 也召回，注入 system 的"经验/偏好"段 | 重复目标（"查 F 盘"×3）第二次起能命中经验；`/api/memory` 可查看/编辑 facts |
| 1-8 | **Playwright 线程模型收敛** | 方案 A：web 通道独占一个 owner 线程，所有调用走队列；方案 B：迁 async + `task.cancel()`。A 改动小、先做 | 连续 20 次网页调用 0 次 `Sync API inside asyncio loop` |
| 1-9 | **流式输出** | API/本地通道开 `stream=true`，SSE 增 `token` 事件；网页通道保持整段（受页面能力限制） | 首字延迟 < 2s（API/本地） |
| 1-10 | **基础工具补齐** | `calc`（安全表达式求值，禁 eval）、`http_get`（正文抽取+长度上限）、`read_table`（CSV/Excel 前 N 行）、`pdf_text`（前 N 页） | "56+24" 不再绕 `run_shell`；表格/PDF 任务可直接做 |

## 附录：统计口径

- 轨迹目录：`.agent/traces/*.jsonl`，共 40 个文件、319 个事件。
- "完整任务" = 存在 `task_end` 事件，36 个；其余 4 个无收尾。
- "假成功" = `stop_reason=finished` 且 `tool_end` 事件数为 0，19 个。
- "限流页" = 最终 `answer` 含 `请求过于频繁 / 验证码 / 登录失效 / 请稍后再试`，5 个。
- 工具失败率 = 该工具 `tool_end.ok=false` 次数 / `tool_end` 总次数。
- 以上均可由 `.venv/Scripts/python.exe` 重算，无需联网、不依赖模型。
